# 輪講スライド生成：設計仕様 v0.1

日付: 2026-11-06。目標は2026-11-08（日）に一連の操作を実演できる状態。これは初期実装の仕様であり、全機能の実装完了を意味しない。

## 1. 目的と利用者

論文紹介を準備する学生が、論文と過去資料から短い依頼で編集可能なPPTXを得る。評価は、内容・表示・編集操作を分け、人が直したい箇所が改善前から減ったかで行う。

「既存相当」は機能一覧で追跡する。既存skillの文章・実装を複製せず、公開ライブラリのAPIとユーザー要件から実装する。利用ライブラリ自体のライセンスは利用物一覧に記録する。

## 2. 主要ユースケース

| ID | 入力・操作 | 期待結果 |

| U02 | 過去PPTXを参考に指定 | 参考範囲を区別し、別研究の内容を混入しない |
| U03 | 自作テーマで生成 | 共通レイアウトと編集可能な要素 |

## 4. システム構成

短い依頼 + 論文 + 参考資料 → AI + 自作skill → deck.json → 検査 → 共通生成器 → PPTX → 構造検査 + 描画 → AI・人の評価 → 構成の修正 → 再生成。

- skill: 内容の理解、構成、説明、出典、修正判断。
- deck.json: AIと生成器を分離する中間データ。モデルや会話の形式に依存させない。
- 生成器: 同じデータから文字・画像・表・図形・グラフ・ノートを組み立てる。
- 構成修正: 安定したページIDへの操作。既存PPTXの人手修正を取り込む機能とは別。
- 検査器: スキーマ、座標、過密の兆候、PPTX内部構造。視覚確認や事実照合の代替にしない。
- サービス: Cloud Run候補。初版は構成JSONからの生成APIで、Geminiによる構成生成の接続は別工程。

## 5. AIとツールの責務

設計・実装はこのチャットのCodex。現在の実行モデルIDをコード側が推測して記録しない。AIが生成した構成は実際のモデル名・依頼文・資料・会話条件を記録する。

初版のダミーJSONは人・コードが用意した試験入力であり、AIが論文を理解した証拠ではない。skillのハッシュ保存も、AIが読んだ証拠ではない。

完成品の構成生成AIはGoogle技術を中核にする大会条件を踏まえ、Geminiを候補とする。利用権限・モデル・価格・品質の確認後に確定する。複数AIを同時に実装するより、まず一つで動かしてから接続部分を追加する。

この環境の付属skillも指示に影響するため、このチャットでの生成を自作skill単独の効果と呼ばない。厳密な比較は、読み込む指示とモデルを管理できる環境で実施する。

## 6. データ契約

`src/schema.mjs` を実行可能な入力スキーマの正本とする。例は `examples/demo.deck.json`。

- バージョン: `version: 1`。不明なキーを拒否する。
- 資料: `title`、`theme`、`slides`。テーマは色、フォント、タイトル・本文サイズ。
- ページ: 一意な`id`、`title`、`layout`、`elements`、任意の`notes`・`sources`。
- 要素: 一意な`id`、`type`、位置・寸法。長さの単位はインチ、文字サイズはpt。
- テキストは`text`、表は`rows`、グラフは`labels`と`series`。
- 画像はローカルの許可された資産ディレクトリ内のファイル、またはPNG/JPEGのdata URL。サーバーではローカルパスを許可しない。
- JSONのページ順が出力順。JSONの要素順が重なり順。
- テーマ参照と個別書式指定を区別する。自由配置の文字サイズを個別指定した場合、一括変更の限界を記録する。

生成ライブラリが共通プレースホルダーへ書き込む個別の文字書式と座標は、自作生成物に限定して除去し、レイアウトから継承させる。対象はこの生成器が定義したタイトル・本文枠のみ。取り込んだ第三者PPTXの書式を一律に除去する処理には使わない。

## 7. 生成と修正の契約

生成前に全入力を検証する。不正入力ではPPTXを生成せず、エラー位置を返す。過密の推定は警告にし、正確な文字組みの判定と偽らない。黙って文章を削除・縮小しない。

CLIは元入力と同じ場所への出力、既存ファイルの上書きを拒否する。PPTX出力後に構造検査を行い、別ファイルで記録する。出力のハッシュを記録する。

修正操作は`replace`（ページID指定）、`insert`（任意の直後ID）、`remove`、`reorder`。全操作後に全体を検証し、失敗時は変更結果を保存しない。修正後も原本JSON/PPTXは保持する。生成器を通した再生成は、人がPowerPointで行った変更の保持を保証しない。

## 8. プレビューと判定

- Windows: PowerPointでの画像出力を使った確認が可能。非表示の読み取り専用で原本を保持する。
- Cloud/Linux: LibreOfficeと日本語フォントを含むコンテナを検討し、PowerPointとの差を確認する。
- 全ページの確認と、縮小一覧での流れの確認を区別する。
- 表示確認が未実施なら、構造検査が通っても納品品質が合格したと表示しない。

## 9. Cloud RunのAPI契約

2026-11-10追記: Cloud Runでは、AIエージェント向けのMCP（`POST /mcp`）を主な入口とし、REST（`POST /render`）を審査・Webデモ向けに残す。両方とも同じ共通コードを呼ぶ。ツール・ファイル受け渡し・認証は[mcp.md](mcp.md)。以下は初版のREST契約。

設計: `GET /health`、`POST /render`。`POST /render` の本文はdeck.json、成功時はPPTX、失敗はJSONエラー。初期コードはローカルサービスとして検証し、デプロイ完了とは区別する。

- `PORT`環境変数、初期値8080。
- リクエスト上限8MiB、ファイルパスの入力は禁止。外部URLを取得しない。
- 原文・画像・秘密情報をログへ出さない。
- アクセス制御はCloud Runの認証を基本とし、公開デモの方針は別途決定する。未認証公開・デプロイはこの仕様作成では行わない。
- 一時ファイルを共有せず、ユーザーの資料をリポジトリに保存しない。
- サービスの公開・生成AI APIの利用費・並列数・保持期間は、実環境の確認後に決める。

## 10. ライセンスと公開データ

依存ライブラリと出典を`docs/dependencies.md`へ記録し、提出時の著作物利用シートへ転記する。Anthropic/OpenAI付属skillのファイル・コードを同梱しない。会社資料・個人情報を含むPPTXは試験例として公開しない。公開するfixtureはダミーと自作素材のみ。

## 11. 既知の境界と変更管理

全てのPPTX・POTXの取り込み、ノート付き複製、ネイティブ数式、SmartArt、動画、フォント埋め込みは初期生成器の対象外。未対応を無視して似た出力へ変換しない。

方針変更はAGENTS.mdと同じPRで更新する。実装完了・実行確認・視覚確認・操作確認を別々に記録する。仕様の行数は品質の保証ではなく、受入試験で動作を判断する。
